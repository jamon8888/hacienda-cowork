# Release v0.33.0 — documents lexical lane, and the hacienda pointer

> **For agentic workers:** tasks are ordered and independently revertable. Task 1 is a gate: nothing
> below it may start until it is green.

**Goal:** cut `v0.33.0` from a green `main`, publish it, and point hacienda-cowork at it so the
documents tier is usable from the app.

**Why now:** `main` has not compiled under `--features full` since #73. Eight commits landed red,
and every open PR (#72, #74, #55, #46) has a `full` job failing for that reason rather than its own.
There is no release path until that is fixed.

---

## Context: what `v0.33.0` is, stated precisely

`v0.33.0` is **not** spec 0012. It is Phase 0 + Phase 2 of spec 0012, plus an unblock.

| Capability | State in this release |
|---|---|
| Documents extraction, chunking, **embeddings** | Active. `[documents] embed` defaults to `true` |
| Lexical-only store (`embed = false`) | **Fixed.** It panicked in arrow on the first batch |
| FTS index over `text` + `heading_path` | Lands. Built once per flush, `optimize(All)` after |
| Conjunctive→disjunctive relaxation ladder | Lands. `(len, lexicographic)` term order, capped |
| `heading_path` per chunk | Lands, for ATX/setext headings only — see #78 |
| Multi-lane RRF fusion | **Not in this release.** Code tier only |
| `exact` / phrase lanes (statute numbers, quoted citations) | **Not in this release.** Phase 3 |
| Facets, `doc_type`, `jurisdiction`, `citation` | **Not in this release.** Phase 4 |

The honest one-liner for the release notes: **semantic search is on by default, and keyword search
now exists. They are not combined yet.**

## Task 1b — the `full` job's real failure was not the compile errors

Recorded after the fact, because the plan above sent the release down the wrong path.

PR #77's CI failed `test / ubuntu-latest / full` three times *after* the compile errors were fixed,
with `Schema Error: Multi-column (composite) indices are not yet supported` from
`ensure_keyword_index`. `KEYWORD_COLUMNS` named `["text", "heading_path"]` and `create_index` was
handed both at once; Lance rejects `columns.len() != 1` outright.

Two facts were true at once and neither was visible:

- the keyword lane had **never built an index**, so it never searched anything;
- `heading_path` was computed by the extractor and dropped before the table, so the index named a
  column that did not exist.

Every smoke test passed anyway, because each queried body text and the build failed before any
assertion ran. The gate was not "does it compile" — it was "does the lane work", and nothing tested
that.

### A wrong turn worth recording: `MultiMatchQuery` is not the bug it looks like

The obvious next hypothesis was that only the index was broken and the query was fine. It is not
fine-looking. `keyword_query` builds one `MatchQuery` per indexed column and hands them to
`MultiMatchQuery`, and `MultiMatchQuery` compiles to `UnionExec`
(`lance-10.0.0/src/dataset/scanner.rs:3437-3451`). An `OR` across columns would make the lane
disjunctive and silently disable `search_relaxed`, whose entire job is to relax an over-strict
conjunction — so the obvious reading is that this is the second half of the same bug.

**It is not.** Reading `UnionExec` and concluding "OR" skips what each member is: a conjunctive
`MatchQuery`. The union is across **columns**, not across **terms**. Measured on
`lancedb 0.37.1` / `lance 10.0.0` with the exact query shape the lane builds:

| query                                         | result       |
|-----------------------------------------------|--------------|
| `terminate arbitration` (one term per column) | `[]`         |
| `terminate lease` (both terms in `text`)      | `[lease.md]` |
| `terminate covenants` (body terms of two rows) | `[]`         |

The third row settles it. A plain union of per-column conjunctions would have returned both rows; it
returns neither. The strict round genuinely matches nothing with `MultiMatchQuery` in place, and the
ladder has something real to relax.

The fix built from that hypothesis — per-column queries unioned in Rust — **did not compile**:
`LexicalHit` has no `score` field, because the lane has never exposed relevance. Its smoke test also
asserted behaviour the measurements contradict. Reverted in `e56e1ec`. The whole cost was one CI
cycle and one commit.

Two things follow, and they are the transferable part:

- **A `UnionExec` in a query plan is not the same claim as "this query is a disjunction."** What
  feeds it is the claim.
- **The red test was already the experiment.**
  `relaxation_rescues_a_query_whose_terms_do_not_all_appear` reproduces the exact failing fixture
  against the real library in about a second, in a standalone crate, without building basemind. That
  probe existed in `~/.local/opt/ftsprobe` and was left running unexamined through two CI cycles.

### The real defect, and the fix

`heading_path` was computed by the extractor onto `DocChunk` and dropped by `build_doc_rows`, so
`documents_schema` never had the column and `ensure_keyword_index` named an index over a column that
did not exist — on top of passing both columns to a `create_index` that refuses two. `e1e3336` fixes
both: the column reaches the table as `""` when a chunk has no breadcrumb, and the indexes are built
one per column with names the code actually asks for, which is what makes the drop-stale branch
reachable at all.

`KEYWORD_COLUMNS` and `KEYWORD_INDEXES` are asserted to name the same columns, so a column added to
one and not the other fails a unit test rather than being silently absent from every search.

### The second failure, once the first was fixed: a test that had never run

With the index actually building, `a_lexical_only_store_answers_a_topical_query` went red:
"the lexical lane must find something in a store it indexed". The lane was fine and the fixture was
not. The corpus reads `non-payment`; the tokenizer emits `non` + `payment`, so the query term
`nonpayment` is a token **no row can ever carry**. The strict round matches nothing, and so does
every relaxed round — the ladder drops terms until one matches, and that one never can.

Measured on `lancedb 0.37.1` with the lane's own tokenizer over that exact corpus:

| query                       | result                        |
|-----------------------------|-------------------------------|
| `nonpayment`                | `[]`                          |
| `payment`                   | `[notice.md, lease.md]`       |
| `terminate lease payment`   | `[lease.md]`                  |
| `terminate lease nonpayment`| `[]`                          |

The test asserted only that the lane finds *something*, so it could not tell "the lane is broken"
from "the query is unanswerable". It stayed green for as long as the index was never built at all —
`build_index_after_ingest` died on the composite-index error before any assertion ran. **A test that
passes because the code under it never executed is not evidence**, and this one had been supplying
exactly that. Every smoke test in this file was in that state; two have now been shown to have been
asserting things that were untrue.

The generalisable form: when a gate has been failing for a reason that masks every assertion behind
it, fixing the gate is not the end of the work. Every test the gate was hiding needs to be
re-examined on its own terms, because "green" and "never ran" look identical from outside.

### The formatting cycle

`cargo fmt --check` runs in the CI matrix and gates everything behind it. One unformatted test in
`tests/document_fts_smoke.rs` failed four jobs before a single assertion ran, which is what made the
`full` job's real failure invisible for a cycle. Run `cargo fmt --all` before pushing.

**Local-verification gap.** The plan's own note warns that `--lib` misses `rrf.rs` tests and cost real
time. The same class of mistake repeated: the run that mattered was not reproduced locally, because
this machine needs a 29 GiB cold `target/` build and several cargo invocations were competing for its
lock. The cheap path was available the whole time and unused — see the probe above.

The plan says to merge #46 because it "retracts a claim that `embed = false` gives keyword search,
which #65/#73 then made true". True that the old claim is false — but #46's replacement is *also*
false as of this release, and worse, it points at a closed issue:

- it adds "there is no full-text index on the documents table";
- it tells the reader to follow **issue #33**, which is `[CLOSED]` and *is* the lexical lane this

Merging it would replace one false claim with another and point users at a closed issue as the reason
a feature they now have is absent. **Rewrite it** to describe the state this release actually ships:
the lane exists, it is lexical-only when `embed = false`, and it is not fused with the vector lane.
`configuration.mdx:178` already reads correctly on `main` and needs no change.

### #55 decision

agent falls back to the shell and reads originals in clear, which was observed on 2026-10-02.

The plan's concern that "clippy and the full suite were never run locally — and could not be,

- `ab5f1b4` take the file identity without following links, open with `O_NOFOLLOW`

That is 813 added lines across 4 files, with `tests/mcp_safe_resources.rs` (243 lines) — the

**Recommendation: include it if its `full` job is green.** The `full` job is now green on #77, so

### The tag is not signed

Every prior tag (`v0.32.0` … `v0.32.3`) is an **annotated** tag, not a signed one — `git tag -v
v0.32.3` reports `no signature found`. There is no GPG key in this environment and no

annotated tag and say so in the release notes. Do not silently downgrade what the plan promised.

## The migration cost users will hit

`MEMORY_SCHEMA_VER = RELEASE_MINOR as u32` (`src/lance/mod.rs:74`). Cutting 0.33 advances
`RELEASE_MINOR` 32 → 33, and #68 adds the `heading_path` column, which changes the Arrow schema
independently. Both invalidate the on-disk LanceDB directory.

**Every existing workspace re-indexes from scratch on first scan after upgrading.** It is automatic
and needs no action, but the first scan is a full one, and it has to happen before search answers
well. This belongs in the release notes, not in a commit message.

## Explicitly not in this release

- **RRF fusion for documents.** `run_search_documents` (`src/mcp/memory.rs:584`) is
  `if lexical_only { FTS } else { vector KNN }`. The two lanes never run together, so there is
  nothing to fuse. Phase 4. `FusionWeights::document_lanes()` exists and nothing calls it.
- **Statute numbers.** `§ 362(a)(1)` → the `exact` lane needs the n-gram index. Phase 3. For legal
  work this is the one that matters most.
- **Numbered legal headings in `heading_path`.** #78.
- **Routing `safe/` to the documents tier.** hacienda #73. It cannot complete before #75 — the
  search tool must reach the documents tier first, or mirror files leave `code_chunks` and search
  returns *nothing*, not degraded results.
- **Rehydration of PII at query time.** Not designed. See basemind #7-#12.
