# Release v0.33.0 — documents lexical lane, and the hacienda pointer

> **For agentic workers:** tasks are ordered and independently revertable. Task 1 is a gate: nothing
> below it may start until it is green.

**Goal:** cut `v0.33.0` from a green `main`, publish it, and point hacienda-cowork at it so the
documents tier is usable from the app.

**Why now:** `main` has not compiled under `--features full` since #73. Eight commits landed red,
and every open PR (#72, #74, #55, #46) has a `full` job failing for that reason rather than its own.
There is no release path until that is fixed.

---

## Context: what `v0.33.0` is, stated precisely

`v0.33.0` is **not** spec 0012. It is Phase 0 + Phase 2 of spec 0012, plus an unblock.

| Capability | State in this release |
|---|---|
| Documents extraction, chunking, **embeddings** | Active. `[documents] embed` defaults to `true` |
| Lexical-only store (`embed = false`) | **Fixed.** It panicked in arrow on the first batch |
| FTS index over `text` + `heading_path` | Lands. Built once per flush, `optimize(All)` after |
| Conjunctive→disjunctive relaxation ladder | Lands. `(len, lexicographic)` term order, capped |
| `heading_path` per chunk | Lands, for ATX/setext headings only — see #78 |
| Multi-lane RRF fusion | **Not in this release.** Code tier only |
| `exact` / phrase lanes (statute numbers, quoted citations) | **Not in this release.** Phase 3 |
| Facets, `doc_type`, `jurisdiction`, `citation` | **Not in this release.** Phase 4 |

The honest one-liner for the release notes: **semantic search is on by default, and keyword search
now exists. They are not combined yet.**

## Task 1b — the `full` job's real failure was not the compile errors

Recorded after the fact, because the plan above sent the release down the wrong path.

PR #77's CI failed `test / ubuntu-latest / full` three times *after* the compile errors were fixed,
with `Schema Error: Multi-column (composite) indices are not yet supported` from
`ensure_keyword_index`. `KEYWORD_COLUMNS` named `["text", "heading_path"]` and `create_index` was
handed both at once; Lance rejects `columns.len() != 1` outright.

Two facts were true at once and neither was visible:

- the keyword lane had **never built an index**, so it never searched anything;
- `heading_path` was computed by the extractor and dropped before the table, so the index named a
  column that did not exist.

Every smoke test passed anyway, because each queried body text and the build failed before any
assertion ran. The gate was not "does it compile" — it was "does the lane work", and nothing tested
that.

### The part that was wrong in the first fix

The first fix built two single-column indexes and left the query naming both columns, on the belief
that Lance's column auto-discovery would union them and that was sufficient. It is not:
`MultiMatchQuery` compiles to `UnionExec` (`lance-10.0.0/src/dataset/scanner.rs:3437-3451`), so it is
an **OR** across columns. `Operator::And` is per-member and cannot prevent this. A row whose body
matched satisfied the query regardless of its heading, which made the lane disjunctive and silently
disabled `search_relaxed` — the relaxation ladder, whose entire job is to relax an over-strict
conjunction, degenerated to a single OR query with extra steps.

`relaxation_rescues_a_query_whose_terms_do_not_all_appear` caught it, and only because a second index
existed to make the union observable. With one column the test could not have failed. The lesson is
that a test which passes for the wrong reason is not a test, and that the assertion belongs on the
query's *shape* as well as its operator.

**Local-verification gap.** The plan's own note warns that `--lib` misses `rrf.rs` tests and cost real
time. The same class of mistake happened again: the run that mattered could not be reproduced locally,
because this machine needs a 29 GiB cold `target/` build and three cargo invocations were competing
for it. Two CI cycles went to a formatting diff and then to this. **Any change to the keyword lane
needs `cargo test --features full --test document_fts_smoke` run before it is pushed**, not after.

### What the fix changed

- `ensure_keyword_index` builds two named single-column indexes, so the drop-stale branch is real at
  all — it compared `list_indices` against a name Lance derived and the code never asked for.
- `heading_path` reaches the table, `""` when a chunk has no breadcrumb.
- `search_lexical` runs one conjunctive query per column and unions, keeping the higher score per row.
- `keyword_query_on` replaces `keyword_query`, and the unit test asserts the query is a single-column
  `Match` — the variant, not just the members.

The union is a **maximum**, not a sum: a chunk matching weakly on its heading and strongly on its body
scores the same as one matching only on its heading. `MultiMatchQuery::try_with_boosts` exists if a
real corpus shows this needs weighting; nothing is weighted because nothing has been measured.

The plan says to merge #46 because it "retracts a claim that `embed = false` gives keyword search,
which #65/#73 then made true". True that the old claim is false — but #46's replacement is *also*
false as of this release, and worse, it points at a closed issue:

- it adds "there is no full-text index on the documents table";
- it tells the reader to follow **issue #33**, which is `[CLOSED]` and *is* the lexical lane this

Merging it would replace one false claim with another and point users at a closed issue as the reason
a feature they now have is absent. **Rewrite it** to describe the state this release actually ships:
the lane exists, it is lexical-only when `embed = false`, and it is not fused with the vector lane.
`configuration.mdx:178` already reads correctly on `main` and needs no change.

### #55 decision

`#55` serves the `safe/` mirror over MCP `resources/list` + `resources/read`
(`basemind://safe/<path>`), with symlink/traversal/size guards. hacienda needs it: without it the
agent falls back to the shell and reads originals in clear, which was observed on 2026-10-02.

The plan's concern that "clippy and the full suite were never run locally — and could not be,
because `main` did not compile" has since been addressed by three commits on the branch itself:

- `b2e6529` bound the `safe/` listing, refuse a linked `safe/`, close the open race
- `ab5f1b4` take the file identity without following links, open with `O_NOFOLLOW`
- `4310627` check where the opened file really is, to catch a swapped intermediate directory

That is 813 added lines across 4 files, with `tests/mcp_safe_resources.rs` (243 lines) — the
reviewer-visible part of the work exists.

**Recommendation: include it if its `full` job is green.** The `full` job is now green on #77, so
merging #77 first gives #55 a `full` run that reflects its own code. If that run is red, ship without
#55 and say in the release notes that the safe mirror is still shell-read.

### The tag is not signed

## The migration cost users will hit

`MEMORY_SCHEMA_VER = RELEASE_MINOR as u32` (`src/lance/mod.rs:74`). Cutting 0.33 advances
`RELEASE_MINOR` 32 → 33, and #68 adds the `heading_path` column, which changes the Arrow schema
independently. Both invalidate the on-disk LanceDB directory.

**Every existing workspace re-indexes from scratch on first scan after upgrading.** It is automatic
and needs no action, but the first scan is a full one, and it has to happen before search answers
well. This belongs in the release notes, not in a commit message.

## Explicitly not in this release

- **RRF fusion for documents.** `run_search_documents` (`src/mcp/memory.rs:584`) is
  `if lexical_only { FTS } else { vector KNN }`. The two lanes never run together, so there is
  nothing to fuse. Phase 4. `FusionWeights::document_lanes()` exists and nothing calls it.
- **Statute numbers.** `§ 362(a)(1)` → the `exact` lane needs the n-gram index. Phase 3. For legal
  work this is the one that matters most.
- **Numbered legal headings in `heading_path`.** #78.
- **Routing `safe/` to the documents tier.** hacienda #73. It cannot complete before #75 — the
  search tool must reach the documents tier first, or mirror files leave `code_chunks` and search
  returns *nothing*, not degraded results.
- **Rehydration of PII at query time.** Not designed. See basemind #7-#12.
